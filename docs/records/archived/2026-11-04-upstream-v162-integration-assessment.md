## 新号起号：建议优先接入

### 实际范围与依赖

核心提交 `641f5dcb984a771c9e99fb78dd4ba1e4822043db`，后续有必读和使用场景补充。建议以后按 v1.6.2 的最终文件取完整闭包，不只取最初提交。

- 14 个起号阶段，加 1 个必读入口，共 15 份 Pipeline、361 个节点。
- 10 个 `qh_level_*` 自定义动作：1-3、1-4、2-1、2-2、2-3、2-4、2-6、2-7、2-8、2-9。
- 任务列表、起号预设、13 张任务说明图，以及 interface 中的分组和 import。
- 新节点与本地无同名冲突；显式 next/on_error 跨出起号模块的引用仅 `back`，主要在起号14回主页链中。另须考虑继承的 Default 超时/恢复、Count 等公共能力。
- 12 个模板引用均已存在于本地资源，不要求额外下载识别模型或新增第三方 Python 包。
- 使用普通 OCR、TemplateMatch、ColorMatch、Click/Swipe 和现有 CustomAction；未发现新的底层控制器或协议要求。

上游说明的起点是**创号已经成功后，新手剧情动画到「六个月前，忍之谷」之间**，目标为中忍，推荐九游。没有覆盖账号注册、短信验证、渠道账号登录的完整自动化，不能将其宣传为从零注册到中忍无人值守。

### 接入必须处理的行为

1. **一次性阶段任务与按账号保存进度。** 不能把教程当成每日 05:00 重置任务。按实例和实际账号绑定记录已完成阶段、预期下一阶段及流程版本；同名实例换号后不能继承旧起号完成状态。初版可继续允许按 `--task 起号NN` 人工选择恢复段，不急于做通用工作流引擎。
2. **成功出口要和队列明确交接。** 上游阶段末端大多自然结束，没有我们的完成登记和 StopTask。当前 HardEndSink 能处理自然 Succeeded，但属于硬结束兜底；接入应明确登记成功阶段并走正常任务交接，失败不能误记完成或直接推进下一段。
3. **新手流程专用恢复。** 除一处 boss 分支，绝大多数节点没有独立 on_error，将继承本地 Default_on_error。我们的通用恢复会回主页/重启游戏再重跑当前入口；上游多数入口要求特定剧情或关卡页，重新启动未必回到该页。需限定可自动恢复的页面、关卡重开点；无法确认时留截图并暂停该起号流程，保留进度供人工接续。
4. **起点/终点确认不能只看单个 OCR 标签。** 多段结束条件都写「第三关」「第九关」，例如起号11/12/13均出现第九关，因此仅用该标签无法可靠推导账号进度。需要阶段 ID、完整页面特征及前后状态共同判断。
5. **步骤可能消耗资源。** 起号05/06/14等包括召唤、强化、升级及竞技场流程。要防止恢复时重复执行这些步骤；新号必须使用独立命名环境，不在现有 main/xiaoli 上试跑教程。

### 值得扩展的基础能力

优先从现有代码扩展三项：一次性阶段任务/检查点、按流程选择恢复策略、关卡动作时序校准。不要为接起号重写现有调度、实例管理或新建另一套执行程序。

现有 `interruptible_click`、可停止睡眠、`ClickDelayState`、双击和录制工具都能复用。但上游起号动作调用的是普通 `interruptible_click`，每次等待为「输入耗时 + 指定 delay」；本地 3v3 使用的是绝对时间轴、额外校准及固定修正。不能直接把起号脚本切换到本地 3v3 的 +60ms 规则，也不能覆盖本地 helper。

10 段脚本静态点击数为 8～45 次，指定等待总量约 22.6～120.9 秒。运行时间和输入延迟有较大累积空间，需按关卡验证触发帧、首段偏移、后续点击语义及停止响应，再决定是否统一为可配置动作序列。把时间数据与执行器分离有复用价值，但不是本次评估已经完成的能力。

## 框架与打包依赖：暂不随起号一起改

上游 v1.6.2 的最终配置是 `maafw==5.12.2`，安装工作流也使用 `v5.12.2`；MFA 固定为 `v2.16.1-beta.1`。这不是我们当前版本之上的升级。

历史上游提交显示曾尝试 5.14.0/5.14.3 并多次回退，MFA 也有升级再回退。提交标题和 release 未充分解释所有回退原因，不能推断为我们也必须同步回退。release 列出 vivo 横竖屏闪退修复，但本轮源码对比未找到对应独立启动节点改动；不能承诺只移植业务节点就获得该修复，也不能据此确认回退原因。

本地 `maafw` 与自编译 MaaPiCli 已对齐 5.14.2 / Agent protocol 8。定制分支当前 `d3a63fd5`，还含 AgentSchedulerBootstrap、独立运行目录/临时任务选择、控制器失败检查及正常退出/请求停止等改动。只把 Python 包降级或用官方产物覆盖，会破坏已验证的客户端/服务端组合，重复上次 protocol 7/8 mismatch。

建议本轮保留 5.14.2。若后续实测发现必须换框架，另开独立工作，联动移植定制 MaaPiCli、匹配 Python binding、编译与回归。若回退到5.12.2，还应核对本地所用 And、ROI引用等资源语义，不能仅以新起号模块能运行就判断整个项目能回退。

Windows get-pip/pip 26.2.2 固定可作为独立 CI 修复评估。MFA版本固定是打包可复现性议题，不是起号运行依赖。本地长期方向仍为保留定制 MaaPiCli、参考 MFA 建模拟器兼容层，暂不全面接入 MFA；当前发布工作流集成 MFA，与本地定制运行链的差异也不能在本次业务移植中悄悄视为已解决。

4. 引入完整起号闭包：14段Pipeline、10个动作、必读、预设/说明图/interface、动作注册；维持默认日常计划不自动执行教程。用独立新账号，从01开始分段实测，先完成01～04验证闭环，再推进到14；成功、暂停、退出、重启续段都要验证。

6. 最后单独评估3v3其它特性和框架/发布依赖；无新证据时保持当前框架组合，不为了版本号追齐重做底层。

现有5项已知测试失败按 current-work 记录保留基线，不能借合入删除 enable/enabled 兼容、改掉已有业务路径来让旧断言通过。本次没有运行全量测试或游戏实测，也不估算未经验证的人日工期；起号源码移植的文本风险较低，完整闭环的行为与实机验证风险中高。
