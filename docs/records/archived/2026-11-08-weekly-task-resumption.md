# 每周逆袭跨周日恢复及深渊工坊周调度核对

## 现象与依据

用户反馈脚本运行跨到周日后，每周逆袭不会重新执行，要求同时检查深渊挑战和工坊挑战，沿用现有调度补齐。

main归档日志 `debug/custom/2026-11-07.log.zip` 显示17:42:28加载完整19项计划，17:44:51提交每周逆袭，17:45:15在「完成回到了主页面」停止；期间没有写阶段完成状态，也没有保留下一周期候选的日志。11月8日05:00状态重载后，阶段1/2的周禁用已从磁盘清除，只剩11月24日到期的阶段3，但整天没有再次提交每周逆袭。重启后读取状态正确，不代表同一个Agent队列会自动找回已经消费掉的任务。

## 原因

`SetManagedTaskPersistentState` 既写状态又登记当前任务的未来候选，但只在本次实际走过阶段完成节点时触发。如果启动时三个阶段已经持久化禁用，每周逆袭直接走完成出口，本次没有写状态，就没有候选。周日05:00即使子节点状态到期，队列也已没有这个任务。

深渊和工坊按整任务禁用：启动时禁用的任务仍保留在pending，执行后则由现有完成登记保留下一周期候选。它们没有上述子节点已完成直接退出的缺口；无需修改正确的活动业务逻辑。

## 改动

- 新增通用完成动作 `RetainManagedTaskUntilStateChange`，在每周逆袭确认回到主页后，复用所选阶段已有禁用期限的最早到期点，再经独立StopTask结束。只登记候选，不重写完成记录，不顺延一周。
- 使用当前任务实例的基础选项过滤节点：仅A不因S阶段的较早期限唤醒，仅S不误启用A，同入口多份配置保留各自选项与恢复时间。阶段1/2仍为周日05:00，阶段3原有月期限保持。
- 如果导航回主页时恰好跨过05:00，仍保留刚到期的已有期限，在安全结束后立即重排，避免错误挂到剩余月阶段。已在本次登记的更早恢复点也不被覆盖。
- 沿用既有状态刷新、候选、Wait→StopTask和安全点调度；不新增时钟线程、不在业务执行中抢占、不修改框架。`--once`不保留未来候选，确认完成后正常退出；永久禁用没有虚构恢复日期。
- 深渊与工坊补实际状态文件和队列回归：分别覆盖启动时已禁用、本会话刚完成两条路径，验证跨周到05:00恢复，再挂起到周五20:00/周六09:00，并保留原任务选项。
