# 3v3网络错误弹窗被当作继续导致长期不恢复（只排查）

## 现象与证据

用户要求先解释3v3长时间卡在网络重试页面，为何不点重试也不重启；本次不修代码、不点击设备、不停止主脚本。

main当前CLI/Agent为1593709/1593972，任务200000017。12:50:34.859的 `debug/loop_deadline_expired/2026.11.08-12.50.34.859_3v3_boss战斗循环.png` 明确显示「网络错误」「与服务器通信超时」「点击重新连接」，弹窗按钮为屏幕中央偏下的「确定」。弹窗后面仍露出底部「点击任意位置继续」。

原生日志 `deps/bin/debug/maafw.log` 显示12:50:34.899命中boss循环超时，12:50:35.607开始反复命中 `3v3继续0`，OCR文本为「点击任意位置继续」，命中框 `[553,676,176,25]`，置信度约0.9995，点击也报告成功。例如13:30:00点击在 `[640,676]`，下一次在 `[661,691]`；均不是网络弹窗的确定按钮。

12:50:35.607至14:21:28.169，这个错误分支识别命中7112次、实际执行Click7112次，约91分钟。14:21:31之后日志进入其它结算节点，再回决斗场和下一场匹配；无法仅凭日志判定恢复来自用户点击还是网络变化。本次14:23只读截图已是下一场进入战斗的加载画面，因此不能描述为取证时网络框仍在。

## 原因

1. `3v3继续0` 仅在底部ROI匹配「继续」，不排除网络错误弹窗遮挡。它正确读到了背景字，但错误地把当前场景判成可继续结算，一直点击背景。
2. 3v3没有覆盖此网络弹窗的识别/确认分支。名为弹窗守护的模块当前未注册sink，默认列表也只有好友取消，没有网络错误处理。
3. boss的240秒LoopDeadline确实触发了。根据2026-10-05的设计，这个超时节点是空next，正常JumpBack回作战/结算路由，用于处理观战和结算，不会直接进入重启。此次回到外层后恰好被错误的「继续」分支接走。
4. 外层 `3v3确定进入了作战页面` 的420000ms是每次run_next的识别等待期限，不是整场绝对时限。每次继续识别和点击都成功，然后JumpBack重新进入父节点的next识别，持续开始新一轮，因此不会累计成7分钟失败，也不进入 `Default_on_error` → 重启。

已核对本地框架源码 `/home/linn/MaaPiCli/source/MaaFramework/Task/PipelineTask.cpp`：run_next每次新建start_clock；无识别命中或截图失败才检查识别超时，识别和动作成功则返回；run循环在空next且非错误时弹出JumpBack父节点。与此次原生日志一致。当前3v3没有覆盖整个结算/断网恢复段的独立绝对截止时间；Agent的统一一小时任务让出表也不包含3v3，本场结束让出节点在此处不可达。

## 结果与边界

这是网络弹窗缺少专用处理、背景「继续」误命中、成功循环绕过超时恢复叠加的流水线缺口；不是截图接口卡死，也不是没有触发boss计时器。网络最初断开的底层原因本次未追查。
