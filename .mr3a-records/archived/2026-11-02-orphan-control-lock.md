# 回收原持锁进程退出后被子进程继承的控制锁

## 现象

小鲤上午启动游戏超过入口时限，随后所有操作都报控制忙碌；多次显式接管持续超时。用户要求修复启动，并将环境维护封装在工具内部。

## 原因

实际持有 control.lock 文件描述符的是一条残留的 ADB 截图进程，原启动进程已经退出。FLOCK 随文件描述符继承，内核全局锁记录仍可能指向最初加锁者；本机内核记录的设备号与当前挂载命名空间 stat 的设备号也不同。原实现按 `/proc/locks` 的 PID、设备号定位，找不到实际仍持锁的进程，因而接管只等待到超时。

清理残留后还发现 Android 会话显示 RUNNING、但未取得地址；按原命名入口正常关闭、启动后恢复。没有变更账号或任务选择。

## 改动

- 根据 `/proc/<pid>/fdinfo/<fd>` 证明该描述符持有排他 FLOCK，再通过对应 fd 的 stat 以当前命名空间的设备号/inode 核验目标文件；不依赖已退出的原 PID 或全局锁表设备号。
- pidfd 打开后仍重新核验持锁事实和用户身份，兼容进程在扫描中退出。将共享同一排他锁的继承者纳入原持锁进程族，回收过继的残留；不按进程名批量终止、不删除或重建锁文件。
- 保留其它实例保护：同族持有另一个实例的控制锁时拒绝停止；新的控制者取得租约时不继续终止新请求。
- 新增真实子进程回归：原父进程已退出而子进程继承锁时可接管；子进程同时继承 main 和 xiaoli 时拒绝，另一实例控制者保持存活。
- 小鲤仓库将接管回收收进 start/stop，并将诊断与内部命令移出主体入口；此仓库继续只提供命名设备与控制租约，不负责 DSH 会话或提示。

- 实际通过固定 xiaoli 控制器回收遗留的截图进程，控制租约恢复可用；按同名 run 完成环境关闭、启动，原启动任务正常结束。
